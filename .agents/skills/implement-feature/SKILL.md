# Implement a backend feature

Read root `AGENTS.md`, `docs/orchestration.md`, `docs/github-workflow.md`, `docs/api-contract.md`, and relevant privacy/data documents. Resolve paths from the backend repository root. Confirm the actual stack and tools from current source and README; Python/FastAPI/MySQL are known, while Python version, app layout, ORM/driver, migrations, auth, tests, lint, and type checking remain undecided until the repository establishes them.

Before planning, the root reads the FE-authored implementation-request specification in the shared Notion page linked by `docs/api-contract.md` and reuses existing APIs. FE owns API specification text; BE implements it and may update implementation status and its PR links. If no specification exists, report the needed API to FE rather than inventing it. Pass relevant specification content to subagents. Feature work includes those related BE status/link updates; read-only/local-only or more specific write restrictions take precedence. Preserve unrelated page content and resolve uncertain write outcomes before retrying.

For nontrivial features, behavior changes, or design-level bug fixes, the root first delegates a plan to a separate Astra medium planner, even when the root's selected model is Astra. Wait for that plan before assigning implementation. The planner returns the user-visible result, affected files and API/database constraints, privacy and permission risks, integrity/error cases, bounded tasks with file ownership and dependencies, acceptance checks, and open decisions. The root owns coordination, acceptance, integration, final verification, and Git delivery.

Small copy or single-element edits and explanation-only requests can stay with the root. User scope and model choices take precedence. If named planner-role invocation is unavailable, use a separate explicitly selected Astra medium agent with planner instructions and report that route. If neither the named role nor that explicit model route is available, report the limitation, continue only independent read-only discovery, and wait for a revised approach before dependent implementation. Do not silently substitute a model.

After planning, delegate bounded implementation to Luna high where supported. Assign exact files, relevant context, constraints, checks, and single-writer ownership for shared contracts or infrastructure. Parallelize only independent work. Workers, testers, and reviewers report to the root and do not recursively orchestrate or perform PR delivery. Use an independent Astra medium reviewer for meaningful API, authorization, privacy, persistence, migration, or behavior changes where available.

Implement the specification FE marked ready for implementation without a separate FE/BE contract approval gate. Ask FE only about missing or contradictory details, infeasible requirements, or security/authorization problems; do not silently change the specification. Hold only affected behavior and continue independent work. FE can use mocks until the implemented backend is available.

Read the specification at task start and compare the implementation with it before reporting completion. If FE changes it during work, clarify the change and update affected implementation and verification. Record the Notion page, method/path, key specification details or changes, and actual check results in the PR. Separate snapshot files, required API IDs/revisions/approvers, four mandatory rechecks, and automatic Draft status while waiting for dual contract approval are not required. If Notion is inaccessible or incomplete, report the limit and continue only work supported by known requirements. No watcher or automatic cross-repository type update is implied.

Apply server-side authorization and validate ownership at each relevant boundary. Preserve private source data and expose only fields permitted by the accepted contract. Treat database constraints, transactions, race conditions, retries, idempotency, and rollback compatibility according to the feature and established project patterns; do not invent a repository architecture or install new dependencies without an approved decision. Return stable, documented error behavior without leaking secrets or private records.

Integrate the work and run relevant commands that actually exist in the repository. Verify API behavior and applicable database/auth/error cases; report unavailable services and unrun checks truthfully. For documentation-only changes, perform applicable document checks and mark application tests not applicable. Report changed behavior, files, checks and results, reviewer findings handled, and remaining limitations.

For implementation requests, complete the authorized issue/branch/commit/push/PR workflow using the repository's `deliver-pr` skill. The root owns delivery. Do not stop at a local implementation when the request includes PR delivery. If required verification or delivery is blocked, report that status. Respect an explicit instruction to keep work local.
