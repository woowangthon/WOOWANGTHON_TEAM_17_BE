# 백엔드 에이전트 운영

## 역할과 모델

| 역할 | 모델 | 책임 |
| --- | --- | --- |
| root | 현재 선택된 세션 모델 | 요구사항·조정·통합·최종 검사·GitHub 전달 |
| planner | Astra medium | 비단순 기능·동작·설계가 필요한 버그의 선행 계획 |
| explorer | Luna high | 관련 코드·계약·경계의 읽기 전용 조사 |
| worker | Luna high | 합의된 범위와 파일의 구현 |
| tester | Luna high | 실제 설정된 검사와 전용 테스트 환경의 검증 |
| reviewer | Astra medium | 독립적인 보안·계약·회귀 검토 |

`.codex/config.toml`은 프로젝트 기본값이며 현재 root 세션 모델을 전환하지 않는다. 역할별 모델은 각 `.codex/agents/*.toml`에 적는다. 동시 하위 에이전트는 최대 2개다. 사용자가 지정한 모델·범위가 우선한다.

## 위임 흐름

- 단순 설명·조사는 root가 직접 하거나 explorer에게 읽기 전용으로 맡길 수 있다.
- 비단순 기능, 실제 동작 변경, 설계가 필요한 버그는 root의 모델과 무관하게 별도 Astra medium planner를 먼저 실행한다. 계획을 확인한 뒤에만 구현을 배정한다.
- root가 먼저 Notion에서 FE가 작성한 구현 요청 명세를 읽고 planner에게 관련 내용을 전달한다. planner는 해당 규격을 구현할 파일·순서·인수 기준·검증 방법을 계획한다. 규격의 빠진 내용이나 구현상 문제는 root를 통해 FE에 확인하며 임의로 새 규격을 정하지 않는다.
- planner 역할 호출을 지원하지 않으면 planner TOML의 지침과 Astra medium 모델을 명시한 대체 하위 에이전트를 실행하고 그 경로를 보고한다. 두 실행 방식 모두 불가능하면 이유를 보고한다. 독립된 읽기 전용 탐색은 가능하지만 설계에 의존하는 구현은 시작하지 않는다. 다른 모델을 조용히 대신 쓰지 않는다.
- root는 계획을 검토하고 파일 소유권을 배정한다. worker는 구현, tester는 범위가 정해진 검사, reviewer는 독립 검토를 맡는다. 단계가 의존하면 순차 실행하고 파일이 독립된 경우만 병렬화한다.
- 하위 역할은 재위임하거나 PR 절차를 반복하지 않는다. root만 오케스트레이션·통합·최종 검사·GitHub 작업을 맡는다. worker는 별도 지시 없이 커밋·push하지 않는다.

## 백엔드 작업 기준

- 기존 코드·README·실제 도구 설정과 `docs/api-contract.md`의 Notion 명세를 따른다. FE가 규격 본문을 작성하고 BE root는 읽기·구현 상태·BE PR 링크 갱신을 맡는다. 하위 역할에는 필요한 명세를 전달한다.
- FE가 구현 요청으로 작성한 명세는 별도 이중 승인 대기 없이 구현한다. 명세의 누락·모순·구현/보안상 문제만 확인한다. 작업 도중 변경은 관련 구현·검증에 반영하고 완료 전 명세와 결과를 대조한다. 실제 저장소에 없는 도구·명령은 가정하지 않는다.
- 요청·응답, 오류 형태, 인증·인가, 개인별 데이터 접근, 멱등성, 동시 수정, 트랜잭션 경계, migration은 기능 범위에 필요한 만큼 명시적으로 확인한다. 결정되지 않은 항목은 작업 전 root에 전달한다.
- 개인 원문과 자격증명은 권한 없이 노출하지 않는다. 민감 데이터와 비밀값이 응답·로그·오류·fixture에 들어가지 않도록 확인한다.
- 단위·정적 검사와 DB 통합 검사를 구분한다. 일반 검사에는 운영 DB나 실제 사용자 데이터를 쓰지 않는다. DB 검사는 프로젝트가 마련한 전용 테스트 환경과 실제 설정된 도구가 있을 때만 수행한다. 환경이 없으면 대체 성공으로 간주하지 말고 제한을 보고한다.
- reviewer는 관련 범위에서 입력 검증, 권한 검사, 데이터 누출, transaction integrity, 동시성·멱등성, 계약 호환 및 회귀를 살핀다.

## 검사·통합·보고

- 저장소에 실제 등록된 명령만 사용한다. 애플리케이션과 도구 설정이 없는 초기 상태에서 테스트·lint·typecheck·migration 명령이 있다고 가정하거나 임의로 설치하지 않는다.
- 변경 후 영향받는 검사와 필요한 전체 검사, 독립 검토를 root가 마무리한다. 각 명령의 통과·실패·미실행과 미실행 이유를 구분해 기록한다.
- 작업자는 변경 파일, 실행한 검사와 결과, 계약·보안 결정이 필요한 미해결 항목을 root에 보고한다.
- 기능 구현·버그 수정은 별도 지시가 없으면 이슈 연결·브랜치·구현·검증·검토 후 root의 커밋·push·PR까지 포함한다. 사람만 병합한다. 로컬 전용 요청은 예외다.

## 다중 저장소에서 열기

Codex가 프로젝트 지침·skills·`.codex` 역할 설정을 자동 발견하는 기준은 primary 프로젝트 폴더다. 백엔드를 이 설정대로 작업하려면 `WOOWANGTHON_TEAM_17_BE`를 primary로 연 새 프로젝트/채팅을 사용한다. 프론트엔드 저장소를 secondary 폴더로 추가하면 교차 참조에 활용할 수 있지만, secondary의 AGENTS·skills·`.codex` 설정이 자동 적용되거나 세션 root 모델을 바꾸지는 않는다. 필요하면 해당 저장소의 관련 문서를 직접 읽는다.

여러 저장소를 함께 수정하는 요청은 repo별 working directory, remote, base와 작업 branch를 명시하고 파일 소유권을 분리한다. 변경 전 각 저장소의 상태를 확인하며, 한 repo의 지침·Git 설정을 다른 repo에 적용하지 않는다.
