# 백엔드 작업과 PR 흐름

## 기본 흐름

이슈 연결 → 작업 브랜치 → (비단순 작업은 별도 planner 계획) → 구현 → 확인·수정·재확인 → 커밋·push → 자체 작성 PR 보고서 → 사람의 리뷰·병합.

사용자가 요청한 백엔드 저장소는 `https://github.com/woowangthon/WOOWANGTHON_TEAM_17_BE`입니다. 전달 시 원격 최신 상태, 인증, 쓰기 권한, 브랜치 보호를 다시 확인합니다. 기존 CI·보호 규칙은 보존하고, 사용자 요청 없이 CI 워크플로를 추가하거나 완료 조건으로 삼지 않습니다. 자동 병합, main 직접 push, force push는 기본 범위가 아닙니다. 사람만 리뷰·병합합니다.

### 여러 저장소 작업 경계

- 작업 시작 시 root가 실제 백엔드 체크아웃 경로, 그 경로의 remote와 base branch를 선택·확인합니다. 프론트엔드가 primary 폴더라는 이유로 그 저장소의 Git 명령이나 PR 대상 선택을 백엔드 작업에 적용하지 않습니다.
- 백엔드 이슈·브랜치·커밋·PR은 백엔드 저장소에서 각각 관리합니다. 프론트엔드 변경도 필요하면 각 저장소에서 별도 이슈·브랜치·커밋·PR로 진행합니다. 한 저장소의 `.git` 디렉터리를 다른 저장소에 사용하거나 두 저장소 파일을 한 커밋에 섞지 않습니다.
- 서로 의존하는 FE·BE PR은 별도로 만들고 서로 링크합니다. 관련 Notion 명세와 구현한 method/path·핵심 내용·실제 검증 결과를 기록합니다. FE가 규격을 작성하고 BE가 구현하며, 실제 서버가 준비되면 FE에서 화면 연동을 확인합니다.
- Codex 프로젝트의 기본 Git/PR 동작은 primary 폴더를 대상으로 할 수 있습니다. review pane에 여러 저장소가 보인다고 해당 동작이 자동으로 백엔드에 적용되는 것은 아닙니다. 백엔드 작업 전 선택한 경로에서 Git 상태와 remote를 다시 확인합니다.

사용자가 로컬 작업만 지정하면 로컬에서 끝냅니다. 설명·조사만 요청한 경우 이슈와 PR을 만들지 않습니다. 그 외 기능 구현·버그 수정은 별도 제한이 없으면 이슈·브랜치·검증·커밋·push·PR 보고까지 포함합니다.

## 저장소와 도구 확인

- 백엔드 체크아웃 경로와 그 안의 대상 저장소, remote, base, 현재 브랜치, 사용자 변경, 기존 이슈·PR을 확인하고 인증 정보는 출력하지 않습니다. 기본/primary 프로젝트 경로와 다를 수 있으므로 의도한 백엔드 디렉터리에서 명령을 실행합니다.
- 작업 시점의 기준 브랜치를 확인해 `codex/<이슈번호>-<짧은-목적>` 형식의 브랜치를 사용합니다. 기존 이슈·브랜치·PR이 있으면 이어서 작업합니다.
- README와 실제 파일을 확인해 Python 버전, 설치·실행 명령, 앱 구조, 의존성, 테스트·lint·type-check 도구를 파악합니다. 현재 이 항목은 미합의이며 명령이나 도구를 지어내지 않습니다.
- 사용자의 변경을 보존하고 작업 파일만 stage합니다. 임시 파일·비밀·무관한 변경을 포함하지 않습니다.

## 설계 및 작업 분리

- 비단순 기능, 동작 변경, 설계가 필요한 버그 수정은 root가 별도 GPT-6.1 Sol high planner에게 먼저 위임합니다. root의 세션 모델과 무관하게 planner 단계를 거치며, 계획을 확인하기 전 구현자를 배정하지 않습니다.
- planner는 사용자 결과, 영향을 받는 파일과 API/DB 제약, 개인정보·권한·무결성·오류 위험, 소유권이 분리된 작업과 의존성, 수락 기준·검사, 열린 질문을 반환합니다.
- 작은 문구·단일 요소 수정과 설명 요청은 root가 직접 처리할 수 있습니다. 사용자가 정한 범위와 모델이 우선합니다.
- planner/reviewer 역할 호출이 미지원이거나 이전 모델에 고정되어 있으면 해당 역할의 동일 지침과 `gpt-6.1-sol`·`high`를 명시한 별도 실행을 사용하고 보고합니다. 명명된 역할 및 명시적 모델 실행이 모두 불가능하면 원인과 미실행을 보고합니다. planner 계획에 의존하는 구현은 보류하고 독립적인 읽기 전용 탐색만 계속하며, 미실행 reviewer 검토를 완료로 표시하거나 다른 모델을 몰래 대체하지 않습니다.
- root가 조율·통합·최종 검사·Git 전달을 소유합니다. worker·tester·reviewer는 root에 결과를 보고하며 하위 역할이나 PR 흐름을 재귀 시작하지 않습니다. worker는 별도 지시 없이 commit/push하지 않습니다. 백엔드 동작을 다루는 변경에는 가능한 경우 별도 GPT-6.1 Sol high reviewer를 사용합니다.

## 확인 및 검토

- 마지막 변경 후 README와 프로젝트에 실제 등록된 명령으로 관련 검사와 애플리케이션 동작을 확인합니다. 저장소에 없는 테스트·lint·type-check 도구를 있다고 가정하거나 새로 설치하지 않습니다.
- 변경 범위에 따라 API 요청·응답, 인증·권한, 데이터베이스 무결성·트랜잭션·마이그레이션과 실패 상황을 확인합니다. 연결된 API나 DB 환경이 없으면 실행하지 못한 검사와 이유를 기록합니다.
- root가 메인 목차에서 기존 기능 페이지를 찾고 공통 규칙과 해당 기능의 구현 요청 명세를 함께 읽어 구현·검증합니다. BE는 규격을 임의 변경하지 않으며 누락·모순·구현/보안상 문제만 FE에 확인합니다. 작업 중 규격이 바뀌면 영향받는 부분을 확인·수정·재검증합니다. 별도 이중 승인 절차나 네 번 재확인을 공통 완료 조건으로 두지 않습니다.
- DB 관련 구현은 `docs/database-schema.md`와 관련 테이블 DDL을 기준으로 컬럼·복합 FK·CHECK·생성 컬럼·동시성 처리를 확인합니다. 문서 추출 일치 검증과 실제 전용 MySQL 환경에서의 통합 검증을 구분하며, 덤프를 읽은 것만으로 DB에 연결·복원했다고 하지 않습니다.
- 검토 지적을 해결한 뒤 영향받는 확인을 다시 수행합니다. 명령별 결과와 미실행 사유를 구분해 기록하고, 실행하지 않은 검사를 통과로 적지 않습니다.
- 문서 전용 변경은 문서 diff와 링크·경로 확인 등 실제 적용 가능한 점검을 기록합니다. 애플리케이션 검사가 해당 없으면 `해당 없음`으로 표시하며 가짜 앱 검사를 만들지 않습니다.

## PR 작성 및 상태

`.github/pull_request_template.md`는 필수 전제가 아닙니다. 기존 템플릿이 있으면 사용하고, 없으면 아래 자체 보고서 형식으로 PR 본문을 작성합니다. 임시 본문 파일이 필요하면 OS 임시 디렉터리에 두거나 stage 전에 제외가 확인된 위치만 사용합니다. `.agent-work/`가 백엔드 저장소에서 무시된다고 가정하지 않습니다.

PR 보고서에는 다음을 기록합니다.

- 변경 목적과 관련 이슈
- 주요 변경 및 범위
- 실행한 명령·결과, 미실행 또는 해당 없음인 검사와 사유
- 관련 Notion 공통 규칙·기능 페이지, 구현한 method/path, 사용한 명세의 핵심 내용·변경 요약과 실제 검사 결과; 내용 재현이 필요하면 관련 본문을 PR/문서에 인용
- 데이터베이스·마이그레이션·롤백 영향; 해당 없음인 경우 그 사실
- reviewer 및 해결한 지적
- 최종 검증 대상과 일치하는 head SHA
- 남은 작업 또는 위험

검증이 충분하고 중요 지적이 해결되면 사람 리뷰를 위해 Ready 상태로 제출합니다. 필수 확인을 할 수 없거나 해결되지 않은 문제가 있으면 Draft로 두고 이유를 씁니다. 인증·네트워크 오류로 원격 제출이 막히면 로컬 결과와 필요한 조치를 보고합니다. 재시도 전 불확실한 원격 쓰기의 성공 여부를 조회합니다. PR 이후 변경이 있으면 검증과 보고서를 갱신하고 최종 SHA를 확인합니다.

GitHub CI는 이 설정에서 새로 도입하지 않습니다. 기존 CI나 보호 규칙이 있다면 그대로 보존하고, 해당 결과는 Codex의 로컬 검증 근거와 구분합니다.

기능 요청에는 해당 Notion 기능 페이지의 구현 상태·BE PR·실제 검증 결과와 메인 해당 행 갱신도 포함됩니다. 규격 본문은 FE가 작성합니다. 같은 기능의 후속 커밋·PR은 기존 페이지를 사용하며 PR마다 새 페이지를 만들지 않습니다. 일부 API만 완료됐으면 해당 범위를 기록하고 기능 전체 상태는 작성 중 또는 구현 요청으로 유지합니다. 읽기 전용·로컬 전용 또는 개별 쓰기 제한을 우선합니다. FE의 구현 요청 명세로 구현·검증을 마쳤다면 별도 API 이중 승인 대기 없이 사람 리뷰를 위한 Ready로 제출할 수 있습니다.
