# 후보 장소 선택과 날짜별 일정 초안

사용자 요청의 3·4단계는 **BE 후보 필터·개인별/단체 점수**, **AI 후보 기반 방문 날짜·순서 초안**입니다. 앞선 [확정 조건 기반](generation-foundation.md)을 재사용하는 내부 Python 서비스입니다. Notion에는 아직 생성·검토 API 계약이 없으므로 새 HTTP 경로나 FE 연결을 추가하지 않습니다. 실제 경로·도보시간·시간표·총예산 검증과 일정 저장은 5단계입니다.

## 확인한 장소 자료

업데이트된 실제 장소 3개 테이블을 읽기 전용으로 확인했습니다. [실제 DDL과 확인 범위](place-catalog-schema.md)를 따릅니다. 장소 1,857개·상세 1,655개·선호 1,857개를 기존 adapter로 읽었으며 중복/고아 진단은 없었습니다. 공용 DB에는 테스트 쓰기·DDL·초기화를 하지 않았습니다.

실제 `preferenceTags`·`vibeTags`의 `|` 토큰을 정확히 비교합니다. confidence의 high/medium/low는 출처 정보이며 안전성·부재·완전성을 보장하지 않습니다. 여섯 0..5 점수도 명시적 의미·가중치 없이 안전 조건으로 쓰지 않습니다. 첫 점수 정책은 검토된 태그 일치입니다.

## 검토 결정과 필수 조건

`app/candidate_selection.py`의 `build_candidate_selection(snapshot, normalization_result, catalog, review, policy)`는 다음을 처리합니다.

- 기존 AI 태그 제안의 구조·근거·출처 중요도와 구간별 도보 값을 다시 검사합니다.
- 명시적인 내부 검토 결정을 source fingerprint·normalization digest·catalog digest에 연결합니다. 다른 버전이나 다른 장소 자료의 검토는 사용할 수 없습니다.
- 각 검토 필드는 확정 문장 전체와 채택한 제안·적용 범위(all/meal/stay)를 가리킵니다. 미검토 필수 avoid/food는 미해결로 남겨 초안 생성을 막습니다.
- 필수 조건은 satisfied/violated/unknown으로 판단합니다. 확인된 위반은 제외하고, 적용 가능한 필수 사실이 미확인이면 초안 후보에 넣지 않습니다. 높은 취향 점수로 필수 위반을 상쇄하지 않습니다.
- 태그가 없다는 이유로 알레르기·음식·접근성 등에 안전하다고 판단하지 않습니다. 필요한 부재 사실은 명시적인 검토 근거가 있어야 합니다.
- 지역은 명확한 충북 전체 또는 알려진 시·군과 별칭으로 해석합니다. 임의 주소 부분문자열로 지역을 추정하지 않습니다.
- 날짜가 필요한 행사는 확인 가능한 날짜 범위와 여행일의 교집합만 허용합니다. 장소 역할·좌표·수동 검토 상태·중복 상세 같은 미확인 사실은 진단합니다.

검토 레코드를 Python dict로 만들었다는 것이 사용자의 승인이나 인증을 증명하지는 않습니다. 호출자는 기존 인증 경계 뒤의 신뢰된 내부 계층이어야 합니다. 공개 검토 API와 권한·사용자 UX는 FE 계약이 준비된 후 연결해야 합니다. 자동으로 모든 제안을 채택하는 편의 경로는 없습니다.

공통 `lodging`·`fixedSchedule` 텍스트가 있으면 해당 문장과 실제 후보 방문 앵커(date/contentid/position)를 명시적으로 검토해야 합니다. 표현할 수 없는 시간·활동 목표를 조용히 버리거나 임의 장소로 바꾸지 않습니다. 도보 20/40분은 개별 WALK 구간 제한으로 보존하며 실제 시간 충족은 5단계에 남깁니다.

## 점수와 후보 전달

검토된 preferred 태그의 양의 일치는 +1, 선호 회피의 일치는 -1입니다. 중복 의미의 같은 태그를 반복해도 가중치가 늘지 않습니다. 각 참여자의 적용 가능한 서로 다른 선호 수로 정규화하고, 참여자 간 영향은 동일합니다. 순위는 **최저 개인 점수 → 평균 점수 → contentid** 순서이며 내림차순 점수·오름차순 ID로 결정합니다. 검토된 선호가 없는 참여자는 중립 0입니다.

필수 제약은 점수 계산에 섞지 않습니다. 개인 점수와 근거는 내부 선택 결과에만 남기며 AI에는 후보의 집계 점수·장소 기본 정보만 보냅니다. 후보 수 상한은 200개입니다. 알려진 요금은 보존하고 미상은 **요금 확인 필요**, 미상 영업시간은 표시하지 않습니다. 어떤 경우도 실제 총비용·운영 가능성을 보장하지 않습니다.

## 날짜·순서 초안과 검증

AI 패키지 0.4.0은 `draft_candidate_itinerary(dates, candidates, fixed_visits=None, max_visits_per_day=8)`와 순수 검증 함수 `validate_candidate_itinerary(...)`를 제공합니다. 후보는 실제 contentid·장소명·역할·지역·허용 날짜·집계 점수와 선택적 검증 좌표/체류시간만 포함합니다. 개인 원문·실제 회원 ID·닉네임·개인 점수·취향 근거를 provider에 보내지 않습니다.

모델이 반환할 수 있는 것은 `days: [{date, contentids}]`뿐입니다. 날짜는 요청된 순서대로 정확히 한 번, ID는 해당 날짜의 후보만 허용합니다. 중복은 명시적으로 검토한 날짜별 고정 방문을 제외하면 거부하며, 고정 위치도 정확히 유지해야 합니다. 없는 장소·날짜·가격·시간·설명을 추가한 결과는 고쳐 쓰지 않고 거부합니다.

최대 31일·후보 200개·하루 1~8개 방문이라는 내부 자원 한도를 적용합니다. 이는 실제 하루 방문 가능량을 검증한 수가 아닙니다. 요청 400KB·응답 256KB로 제한하고 실제 provider 호출은 60초 timeout과 안전한 typed 오류를 사용합니다.

BE `app/generation_draft.py`의 `generate_candidate_draft(...)`가 선택 결과를 직접 구성하고 검토 준비 상태를 확인합니다. 모델 호출 전·후에 별도 콜백으로 기기 권한과 확정 source·장소 digest를 재검증합니다. 전체 deadline은 전후 조회까지 포함하며 외부 호출 중 DB 연결과 잠금을 유지하지 않습니다. provider에 넘기는 mutable 인자는 검증 기준과 분리한 복사본입니다.

결과 장소명·요금·영업시간·좌표는 AI 응답이 아니라 캡처한 DB 카탈로그에서 연결합니다. 모든 결과는 `requiresReview=true`이고 경로·시간·예산·도보·영업시간 검증은 false입니다. 지도에 쓸 contentid와 latitude/longitude·WGS84는 유지하지만 실제 카카오맵 렌더링·도로 이동시간 조회는 포함하지 않습니다.

## 사용 순서와 남은 범위

1. 기존 기기 인증을 연결한 내부 callback으로 확정 snapshot을 캡처합니다.
2. 짧은 읽기 트랜잭션에서 catalog와 지원 태그를 준비하고 연결을 닫습니다.
3. 확정 취향을 구조화하고, 신뢰된 검토 결정으로 필수 의미와 고정 방문을 정리합니다.
4. `build_candidate_selection`으로 후보·제외/검토 사유·개인/단체 점수를 확인합니다.
5. `generate_candidate_draft`로 날짜별 후보 방문 순서를 제안받습니다. 이후 적용·저장 단계는 현재성을 다시 검사해야 합니다.

Google 호출 없는 fake provider와 synthetic 데이터, 기존 전용 MySQL 환경으로 검증합니다. 실제 모델 품질·경로 가능성·브라우저 표시를 검사했다고 주장하지 않습니다. 최종 명령·개수·head·독립 검토 결과는 연결 PR에 기록합니다. 새 runtime 의존성·migration·CI는 없습니다.
